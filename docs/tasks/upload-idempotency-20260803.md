# 上传接口幂等改造

## 结果

- `init` 使用用户、目标目录、规范文件名和文件哈希生成确定性幂等键，并用请求指纹识别同一资源下的参数冲突。
- 数据库通过唯一索引收敛并发初始化；竞争失败的请求回查并返回赢家创建的任务。
- `chunk` 新增独立分片元数据表，以 `(task_id, chunk_index)` 唯一约束保证相同分片重复上传可复用、内容变化返回 409。
- `merge` 使用带过期时间和持有者标识的 CAS 租约，使单个请求执行合并；竞争请求返回 202，完成后的重复请求返回同一 `file_id`。
- 前端识别 `uploading`、`merging`、`completed` 三种状态，并以可取消的指数退避方式轮询幂等 merge 接口。
- 迁移逻辑使用与运行时一致的身份算法回填旧任务；历史重复任务保留一个规范键，其余任务分配稳定的 legacy 键，并回填已完成任务的 `file_id`。
- Swagger 已同步 multipart 分片参数以及 200、202、400、409 响应契约。

## 验证

- `pnpm verify` 通过：Lint、TypeScript、前端 96 项测试、前端生产构建、后端构建和后端全量测试均成功。
- `go vet ./...` 与 `go test -race ./... -count=1` 通过。

## 教训

- 幂等性必须由数据库唯一约束或 CAS 保证，单纯“先查询再创建”无法抵抗并发请求。
- 文件系统副作用需要与数据库状态共同判断；只有分片记录而磁盘文件缺失时，应允许相同内容重新上传修复。
- 给已有表增加唯一键时，必须先处理旧数据和历史重复记录，否则自动迁移可能在创建索引时失败。
- 合并状态不能只用永久布尔锁；带过期时间和持有者标识的租约才能同时处理并发竞争与进程崩溃恢复。
